## 2. The rule

Source: <https://learn.microsoft.com/en-us/startups/standard-benefits/unlock-more-benefits> (page dated 2026-11-03,
read 2026-11-05).

- "Use at least 5 Azure workloads over a sustained period of 60 days."
- "The 60-day clock starts once you have the required number of workloads, each with at least $1 in spend, and every
  workload must stay above $1 in spend for all 60 days."
- "If any workload drops below the threshold, you fall under the required number."
- A workload is "an Azure service you actively use in your solution. Each unique service counts."
- Milestone 4 ($50,000) has the same rule with **7** workloads. The page says you can skip milestones.

The page does not say how Microsoft counts a "service". We count one Cost Management **ServiceName** as one workload.

## 7. The commands

```
NODE_USE_ENV_PROXY=1 node scripts/m3.mjs prices      # every hard-coded price against the live retail API
NODE_USE_ENV_PROXY=1 node scripts/m3.mjs apply       # DRY RUN: prints exactly what it would create or change
NODE_USE_ENV_PROXY=1 node scripts/m3.mjs apply --apply --start-now [--vm] [--pg-downsize Standard_B2s]
NODE_USE_ENV_PROXY=1 node scripts/m3.mjs status      # any day: spend by service, the clock, yesterday's ledger, the report
```

- **Steps.** `apply` runs guard, image, acr, container, jobs, actiongroup, alerts. Use `--only image,acr` to run some.
- **Safe to repeat.** Each step reads first and writes only on a difference. Nothing is ever deleted.
- **Model deployment.** `--models-deployment taxila-brain` puts the model lane on sol. That needs 18× fewer tokens:
  about 17 calls a day instead of about 280.
- **End date.** `--until` changes when the keeper stops spending (default 2027-01-31).

## 8. How the 60-day clock is tracked

**m3-keeper** (ACA job, cron `17 3,15 * * *` UTC, 0.5 vCPU):

- **Ledger.** Each day's spend per lane goes in `m3/ledger/YYYY-MM-DD.json`, in a private container on `taxilaforge`.
  - The 03:17 run spends up to each lane's target.
  - The 15:17 run tops up only what is missing.
- **No double spend.** Each batch's worst case is written before the batch runs. A crash or a lost write can only make
  the next run spend less, never twice.
- **Unreadable ledger.** The 03:17 run spends each target once and the 15:17 run skips.
- **Failures.** A lane that fails 3 batches in a row switches to its fallback: `taxila-brain` for models, the second
  Speech region for TTS, lower concurrency for storage. A lane that still ends short exits 1, and the job retries up to
  2 times.

**m3-verify** (cron `41 6 * * *` UTC, 0.25 vCPU):

- Asks Cost Management for the last 66 days by ServiceName.
- Computes the clock: consecutive closed days on which **one fixed set** of ≥ 5 services each stayed ≥ $1. That is the
  strict reading. A rotating set does not count.
- Writes `m3/report/YYYY-MM-DD.json`.
- Prints `M3-OK {streak, start, completes, …}`, or one `M3-ALERT` line for each of these:
  - fewer than 6 services ≥ $1 on a closed day;
  - a portfolio service under $1.10;
  - yesterday's ledger missing or short;
  - the clock reset;
  - the cost query failed.

**Alerts.** Both rules notify the action group `m3-owner`, which goes to whoever holds the Owner role on the
subscription:

- `m3-alert-lines`: any `M3-ALERT` line.
- `m3-verify-silent`: no `M3-OK` for 26 hours. That means the verifier is dead, or nothing has been healthy for a day.
  It stays quiet for the first 26 hours after it is created (the `m3-armed-at` tag; a re-run of `apply` keeps it), so a
  fresh setup never sends a false alarm before the verifier's first run.
- Who gets them: the Owner-role receiver reaches only people assigned Owner **directly**. If you hold Owner through a
  group, set `M3_ALERT_EMAIL=<your address>` in `.env.local` before `apply`; it adds an email receiver (never stored in code).

The existing `taxila-job-failures` rule also fires on a failed job run.

**Timing.**

- Day 1 is the first full UTC day after `apply`. That date is `M3_SINCE`, and no earlier day ever alerts.
- Cost Management closes a day 1-2 days later, so day N shows up in `status` on day N+2.
- After `--until`, the keeper spends nothing and the verifier stops alerting. The jobs themselves stay; nothing is
  deleted.

## 9. Known risks

- **Counting.** Microsoft may not count by ServiceName. If Foundry Models and Foundry Tools count as one service (both
  bill on AIServices accounts), we have only 5, or 6 with the VM. That is the best argument for `--vm`.
- **Old names.** If Cost Management ever shows both under the old name "Cognitive Services", the verifier reads Foundry
  Models as $0 and alerts.
- **Rate limit.** The model lane shares `taxila-fast`'s rate limit with the app: ~1.1M output tokens over ~40 minutes,
  at 6 calls at a time. A dedicated deployment, or `--models-deployment taxila-brain`, avoids that.
- **First of the month.** Container Apps' monthly free grant (180,000 vCPU-seconds) is used up on the 1st of each
  month. October still showed ≥ $1 on the 1st, but watch that day.
- **First Premium day.** The day `taxilacr` moves to Premium may be billed pro rata. Day 1 is the next full day.
- **Script size.** Each job's script is passed inline as a container argument: ~25 KB for the keeper, ~20 KB for the
  verifier (the latency job used ~8 KB). If ACA refuses that size, build a small image with the two files instead.
- **Prices.** These are retail list prices. We assume the sponsorship bills at retail. The verifier's Cost Management
  numbers are the check.
