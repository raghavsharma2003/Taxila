## 4. What runs

**m3-keeper, two runners, one ledger** (`m3-ledger/ledger/YYYY-MM-DD.json` on `taxilaforge`):

| runner | where | when (UTC) |
|---|---|---|
| ACA job `m3-keeper` | taxila-env, eastus2 | `17 */3 * * *` = 00:17, 03:17, ... 21:17 |
| systemd timer on `taxila-m3-vm` | centralindia | `01/3:47` = 01:47, 04:47, ... 22:47 (90 minutes after each ACA run) |

How a run works:
- **Lease.** The run creates the day's ledger if it is absent, takes a 60 s **blob lease** (renewed every 20 s), reads
  the ledger under the lease, and writes only with the lease id. A run that finds the lease held does nothing; the
  next slot tops up.
- **Spending.** The first run of a day spends each lane to its target. Later runs top up only what is missing.
- **No double spend.** Each batch's worst case is written before the batch runs (write-ahead). The next lease holder
  adopts a dead run's write-ahead as `orphanUsd`, and it stays counted.
- **Closed loop.** The run reads the latest verifier report. If a lane's service billed under **$1.20** on the last closed
  day, today's target is multiplied by target/actual, so the next bill lands back on the target. The target is capped
  at **$2.50**, and that day's cap becomes target + $0.15. The raise is recorded in the ledger's `targets` with the
  reason, and it never drops within a day.
- **401 / 403.** An immediate `M3-ALERT {"reason":"auth-failed","lane":...}`, and the lane moves to its next endpoint
  at once. A 404 on a deployment does the same (`deployment-missing`).
- **Day boundary.** No batch starts in the last 20 minutes of a UTC day, so a batch's usage never bills on the next day.
  After `M3_UNTIL` (2027-01-31) nothing is spent.

**Without the shared ledger:**
- A **corrupt** ledger: nobody spends, and it alerts.
- A ledger that cannot be **reached** (network, 5xx) or is **refused** (401/403):
  - The ACA runner spends nothing.
  - The VM, **only in its 22:47 slot**, spends each lane to its target against its local mirror of the last shared
    ledger it saw. It keeps that spend in `/var/lib/m3/offline-D.json` and folds it into the shared ledger
    (`offlineUsd`) once it can reach it again.
  - This replaces the v1 rule, under which the morning run spent each target once without the ledger. With two runners
    that rule could spend twice.

**m3-verify** (cron `41 6,18 * * *`, twice a day) works in M4 mode:
- It counts the streak with 7 required and alerts when fewer than **8** services were at or above $1 on a closed day.
- It also reports the M3 reading (5 required).
- A portfolio service under $1.10 prints `M3-WARN` (no email): with 9 services, 8 still counts as OK.
- It also alerts on:
  - a runner (`aca` or `vm`) missing from yesterday's ledger;
  - a 401 that a keeper run recorded (the VM's journal is not in Log Analytics, so the verifier raises it again);
  - a whole-subscription day over **$60** (Vyakti's GPU jobs use the same credit);
  - a projected credit under **₹15,000** at M3_SINCE + 66 days, from `M3_BALANCE_INR` (default ₹230,490.71, read
    2026-11-06 from the MCA billing profile) against each day's Cost in INR;
  - the principal's secret within 21 days of expiring (`M3_SP_SECRET_EXPIRES`, default 2027-03-30). This one fires even
    after M3_UNTIL;
  - a reset of the 7-service streak. A report written under M3 is never compared with an M4 one, so switching milestones
    raises no false reset;
  - a failed cost query.

**Alerts:**
- `m3-alert-lines` fires on any `M3-ALERT` line.
- `m3-verify-silent` fires when there has been no `M3-OK` for 26 hours.
- Both notify `m3-owner`: the Owner role, plus one email receiver for each address in `M3_ALERT_EMAIL` (comma-separated;
  addresses are never written in code).

**Locks.** `m3-credit-do-not-delete` (CanNotDelete), set by you on 2026-11-06, protects:
- taxila-m3-rg (which covers everything M4 creates);
- taxilacr, taxilaforge, taxila-cin-pg, taxila-env and taxila-ai-centralindia;
- m3-keeper, m3-verify, m3-owner, m3-alert-lines and m3-verify-silent.

The `locks` step:
- reads the locks and reports each one as present;
- creates the same lock on a new target, when the principal may (it now holds User Access Administrator);
- otherwise prints the portal and Cloud Shell steps.

`raghavsharma1729-compan-resource` is not locked on purpose: a lock would block another project's deployment deletes.
No step ever needs a DELETE.

## 5. Failure modes

| failure | what catches it | how fast |
|---|---|---|
| a keeper run dies mid-lane | write-ahead + the lease expires in 60 s; the next slot (ACA retry, or the VM 90 min later) adopts it and tops up | ≤ 90 min |
| two runs at once (ACA + VM, or two ACA executions) | the lease: the second does nothing | immediate |
| the ACA job never runs / taxila-env or eastus2 compute is down | the VM runner; the verifier's `runner-missing` | spend ≤ 3 h; alert ≤ 12 h after the day ends |
| the VM is down or deallocated | the ACA runner; `runner-missing`. Virtual Machines may fall under $1 that day (one spare: 8 left is OK) | spend ≤ 3 h; alert ≤ 12 h after the day ends |
| the ledger is unreachable for a while | each run skips with M3-ALERT; one of the 16 daily slots spends when it returns | ≤ 90 min after it is back |
| eastus2 storage is down all day | the VM's 22:47 local fallback (models via southindia, TTS via centralindia). The storage lane is lost that day (8 left) | same day; the next run folds it in |
| the ledger is corrupt | nobody spends; `ledger-corrupt` alert at the next ACA slot; `ledger-short` from the verifier | ≤ 3 h. Fix: overwrite the blob with valid JSON |
| the primary deployment is deleted (404) or throttled (429) | the fallback chain: taxila-brain, then southindia taxila-fast-bg | the same batch (404), 3 batches (429) |
| a key is rotated (401/403) on a lane | immediate M3-ALERT; the next endpoint | immediate (ACA); ≤ 12 h (VM, through the verifier) |
| the storage key is rotated | both runners alert `auth-failed lane ledger`; the VM's 22:47 local fallback keeps models and TTS up | immediate alert |
| a lane bills less than the keeper thinks | the closed loop raises the next day's target (actual < $1.20) | about 2 days (Cost Management lag) |
| a spare stops billing | `M3-WARN` (8 left); `M3-ALERT services-below-min` at 7 | ≤ 12 h after the day closes (2 days after the day) |
| someone tries to delete a resource | the CanNotDelete locks | immediate |
| someone **stops** (not deletes) PG, the VM or taxila-web | locks do not stop this; the verifier counts the loss (one stop = 8 left = WARN) | about 2 days |
| the verifier dies, or nothing is healthy | `m3-verify-silent` (no M3-OK in 26 h) | 26 h |
| the Cost Management query fails | `cost-query-failed` | at the run |
| a burst day (Vyakti's GPUs) | `burst` (> $60 on a recent closed day) | about 2 days |
| the credit runs low | `runway-low` (projected < ₹15,000 at day 66) | twice a day |
| the principal's secret expires (2027-03-30) | `sp-secret-expiring` from 2027-03-09 | daily |
| you stop developing Taxila / Vyakti | the 9 services do not depend on either project, except Container Apps (taxila-web) | — |

## 9. Assumptions to verify live (not measurable before apply)

- **Unattached Standard public IPs bill $0.005/h.** The retail API has no separate idle meter for Standard IPs, but our
  only billed IPs are attached ones. If Virtual Network shows about $0.36, not $1.56, on the first closed day, attach
  the other 10 as secondary ipconfigs.
- **8 rules with a NIC-based backend bill $1.32.** Cost Management's meter quantity should read 24 "Included" + 72
  "Overage" hours for taxila-m3-lb.
- **Managed Run Command passes a named protectedParameter as an environment variable.** The script also reads `$1` as
  a fallback, and stops with `M3-RUNNER-FAIL` if neither is set.
- **The Run Command inline script (~22 KB) is under the service's limit.** Run Command uses the VM's outbound, which
  pip-01 provides.
- **Azure's blob lease semantics**, as coded:
  - a write without the lease id is refused with 412;
  - acquiring a held lease gives 409;
  - leases expire after 60 s.
- **Locks and child resources.** An ACA job or app is not a child of the environment, so the taxila-env lock does not
  block deleting them (the jobs carry their own locks). A lock does not stop a server or VM from being stopped.
- **Microsoft counts a workload as a ServiceName** (unchanged from M3). This is the reason for carrying 2 spares.
